## Current execution paths

### PowerCRUD bulk launch

1. `AsyncMixin.should_process_async()` uses view configuration and `bulk_min_async_records`; backend availability checks the `django_q` import spec and app registration. A false result leaves the caller on the synchronous route. The mixin imports `AsyncManager` at module load. See [`async_mixin.py`](../../../../src/powercrud/mixins/async_mixin.py#L1) and [selection/availability](../../../../src/powercrud/mixins/async_mixin.py#L61).
2. `_handle_async_bulk_operation()` resolves the configured manager class/config, checks current conflicts, creates a task UUID, prepares model/selection/user data, and calls `launch_async_task()` with a CRUD worker dotted path. It passes `manager_class` and `manager_config` as worker kwargs; bulk update also passes persistence backend path/config. The response reverses `powercrud:async_progress` and returns the logical task key. See [manager selection](../../../../src/powercrud/mixins/async_mixin.py#L111) and [bulk launch/response](../../../../src/powercrud/mixins/async_mixin.py#L358).
3. `launch_async_task()` accepts a callable/path, worker args, conflict IDs, lifecycle metadata, optional `task_key`, and q2-shaped options. If `task_key` is absent, a trailing UUID-looking positional string is removed from worker args and used as the key. It reserves conflicts, initializes progress, adds `task_key` to worker kwargs, derives timeout from `Q_CLUSTER`, then calls q2 with the hard-coded completion hook. q2's returned ID is kept only in the create lifecycle payload and log; the method returns the logical task name. See [signature and arguments](../../../../src/powercrud/async_manager.py#L324) and [launch sequence](../../../../src/powercrud/async_manager.py#L379).
4. After enqueue returns, launch adds the task to active membership; that method reinitializes pending progress. It then emits `create` and returns the task name. Enqueue therefore precedes active registration and create; the current behavior and fast/synchronous completion risk are assigned to Phase C, not fixed here. See [post-enqueue registration](../../../../src/powercrud/async_manager.py#L474) and [active registration](../../../../src/powercrud/async_manager.py#L601).

The other production launch path is direct application use of `AsyncManager.launch_async_task()`; Phase A's source inventory found two built-in PowerCRUD launch call sites in the async mixin. The full inventory of manager/custom launch sites and transaction implications is recorded in [A2 saved-inputs/context findings](../phase_A/phase_A_a2_results.md#saved-inputs-and-context-propagation). No current built-in save-then-enqueue defect was demonstrated there. Q8 still requires launch only after worker inputs have committed.

### Worker, manager reconstruction, progress, and context

1. `bulk_delete_task` and `bulk_update_task` are importable PowerCRUD workers. They pop manager path/config and persistence backend metadata, find the task key in `task_key` or legacy `task_name`, resolve a manager, and update progress around CRUD work. Both return a boolean; caught exceptions are logged and returned as `False`. See [`tasks.py`](../../../../src/powercrud/tasks.py#L19) and [bulk update worker](../../../../src/powercrud/tasks.py#L89).
2. `AsyncManager.resolve_manager()` imports the configured dotted path, checks it is an `AsyncManager` subclass, and constructs it with supplied config when possible. Resolution/configuration exceptions are caught and fall back to the base class. Dictionary config coercion imports `powercrud.async_dashboard` and recognizes `ModelTrackingAsyncManager`, coupling generic reconstruction to PowerCRUD's dashboard module. See [manager reconstruction](../../../../src/powercrud/async_manager.py#L1231).
3. `task_context()` stores only `task_name` and optional manager class path in a `ContextVar`. `register_descendant_conflicts()` converts IDs to integers, resolves a model label where possible, imports the base PowerCRUD manager, and adds locks through it; it does not use the stored manager path/config. See [`async_context.py`](../../../../src/powercrud/async_context.py#L37). The module docstring says bulk workers enter context automatically, but A2 source inspection found no automatic entry in the inspected workers/persistence paths; sample tests enter it explicitly. Treat automatic worker propagation as unverified/currently absent in those inspected paths.

### Completion and optional model tracking

1. q2 receives `powercrud.async_hooks.task_completion_hook`. The hook module imports `django_q.models.Task` at module import; the function parses task kwargs, extracts manager path/config, imports `powercrud.async_manager.AsyncManager`, resolves a manager, and passes the q2 Task object plus `Task.name` to completion handling. A broad catch logs and suppresses hook errors. See [`async_hooks.py` imports](../../../../src/powercrud/async_hooks.py#L13) and [completion dispatch](../../../../src/powercrud/async_hooks.py#L58).
2. `handle_task_completion()` removes active/lock/progress artifacts and maps q2 `success` to lifecycle `complete` or `fail`; an unknown success value currently emits a `complete` event with unknown status. Lifecycle callbacks are best effort through `_emit_lifecycle()`. See [completion translation](../../../../src/powercrud/async_manager.py#L1169) and [lifecycle dispatch](../../../../src/powercrud/async_manager.py#L144).
3. `ModelTrackingAsyncManager` persists lifecycle events to an application-specified model path with field mappings and formatters. It imports the base manager and PowerCRUD logging; the sample subclass targets `sample.AsyncTaskRecord`. Tracking is reusable in intent, while sample model formatting and dashboard CRUD views are consumer-owned. See [`async_dashboard.py`](../../../../src/powercrud/async_dashboard.py#L21) and [`SampleAsyncManager`](../../../../src/sample/async_manager.py#L8).

### Polling, URLs, and cleanup

1. `AsyncManager.as_view()` reads `task_name`, instantiates the manager, obtains cache-only progress/status, and then falls back to q2 status lookup when progress is absent. The cache-only helper maps missing progress to the literal `completed`, which the view reports as success and stops polling. This is a known issue 6 behavior for Phase C. See [polling view](../../../../src/powercrud/async_manager.py#L1024) and [cache-only status](../../../../src/powercrud/async_manager.py#L565).
2. `get_url()` returns a bare path; `get_urlpatterns()` includes `powercrud.urls` under the `powercrud` namespace. The package URL module conditionally exposes the progress endpoint when q2 is installed. The async mixin and sample views reverse `powercrud:async_progress`. See [URL helpers](../../../../src/powercrud/async_manager.py#L1117), [`powercrud/urls.py`](../../../../src/powercrud/urls.py#L1), and [consumer reverse](../../../../src/powercrud/mixins/async_mixin.py#L467).
3. `pcrud_cleanup_async` and `cleanup_async_artifacts()` both read `POWERCRUD_SETTINGS["ASYNC_ENABLED"]` and return without cleanup when false. When enabled, each constructs `AsyncManager` and calls `cleanup_completed_tasks()`. The generic manager queries q2 ORM `Task` rows by task name; a missing row currently triggers artifact cleanup, and `cleanup_active_tasks()` clears all tracked active tasks. See [management command](../../../../src/powercrud/management/commands/pcrud_cleanup_async.py#L18), [schedule](../../../../src/powercrud/schedules.py#L7), and [reconciliation](../../../../src/powercrud/async_manager.py#L684).

## Design handoff

### Separation constraints already agreed

- Coordinator owns shared state/locks, task state and progress, lifecycle, context, manager reconstruction, optional model tracking, reusable endpoints, and reconciliation/cleanup.
- The q2 adapter owns q2 loading/options, enqueueing, result retrieval/translation, execution identifiers, q2 hooks, probes, and scheduling integration.
- PowerCRUD owns settings translation, bulk decisions, CRUD workers/persistence, conflict presentation, progress modal, dashboard CRUD, sample/domain behavior, and compatibility wrappers.
- Keep dependency direction one-way. q2 models/types/options and CRUD components must not become coordinator-owned public concepts. Preserve legacy entry points under Q9; plan namespace/path migration with the agreed drained-upgrade procedure.

### Preserve during Phase B

Keep task key return and hook/URL/import compatibility, manager subclass construction, current q2 option behavior, cache prefixes, lifecycle payload shape, and existing test expectations while moving ownership. Do not infer global enablement semantics from current inconsistent checks. Do not silently narrow claimed Redis, Memcached, DatabaseCache, broker, or result-storage support.

### Phase C corrections and evidence gaps

Phase A assigns these intentional behavior changes to C: safe dormant imports and targeted explicit-use validation; consistent launch enablement; truthful unknown/missing progress and retained terminal result; business outcome translation; fast/sync launch ordering; concurrent registry and owner-safe expiring locks; conservative missing-result reconciliation; and strict manager identity/config propagation. See [A1 clauses C2–C6](../phase_A/phase_A_notes.md#a1-draft-contracts-for-discussion) and the [hardening register](../0_async_hardening-notes.md#key-async-hardening-issues).

Evidence gaps include actual q2 worker completion; cached-result and save/pruning completion hooks; behavior across the supported q2 range; broker modes claimed by docs versus runtime settings; Redis/Memcached/DatabaseCache shared-state concurrency; lease renewal/failure/recovery; transaction visibility for caller-created inputs; and genuinely absent-q2/import-before-settings proof. Phase A source review at q2 1.11.1 and synchronous/file-cache tests do not close these gaps.

### Questions for the boundary design

1. Which current source modules remain the internal implementation locations for Phase B, and which old paths become compatibility shims? This audit maps ownership only.
2. What explicit coordinator configuration object/values must callers provide, and which existing `POWERCRUD_SETTINGS` values does PowerCRUD translate into it? Preserve existing defaults/precedence until the design resolves this.
3. Where should adapter-facing effective q2 options, q2 ID/result locator, and completion hook metadata be represented so coordinator state does not depend on q2 types?
4. How should legacy `powercrud.async_hooks.task_completion_hook` route to the adapter while remaining importable by q2 workers and downstream consumers?
5. Which endpoint and cleanup entry points are coordinator facilities versus PowerCRUD wrappers, and how will URL namespace and cache-key continuity be maintained?
6. What focused tests should pin structural parity without presenting sync probes, mocks, or sequential tests as worker/concurrency guarantees?

These are design decisions; the audit does not select an architecture or claim any hardening issue complete.
