### Saved inputs and context propagation

PowerCRUD bulk views choose queueing and call launch_async_task() from the request path in [async_mixin.py:358–451](../../../../src/powercrud/mixins/async_mixin.py#L358). No transaction.on_commit() wraps enqueue. The actual database transaction blocks are in [operation_mixin.py:315 and 431](../../../../src/powercrud/mixins/bulk_mixin/operation_mixin.py#L315); [bulk_persistence.py](../../../../src/powercrud/bulk_persistence.py#L79) delegates to that implementation. These are worker/persistence transactions, separate from a caller's transaction before submission. The two built-in enqueue sites submit IDs and field values for existing rows; no built-in save-then-enqueue defect or outer request transaction was demonstrated. The missing after-commit protection is a risk for callers that create or change worker inputs within a transaction, and needs a targeted regression rather than a blanket change to every submission. The existing no_transaction_atomic fixture also prevents mocked persistence tests from proving visibility. Apply Q8's rule: workers must not start until input writes have saved successfully; inspect each launch site and use transaction.on_commit where required. No mandatory outbox or new submission-state model absent evidence of need.

task_context() is explicit ([async_context.py:49–90](../../../../src/powercrud/async_context.py#L49)). Inspected built-in workers and bulk persistence call sites do not enter it automatically; sample context tests enter it directly. Descendant registration currently constructs the base manager after reading context, losing configured subclass identity. Current tests cover explicit context semantics with mocks; they do not prove context propagation through q2 serialization or a real worker.
