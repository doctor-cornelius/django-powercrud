## Launch ordering

`CoordinatorManager._launch()` reserves conflicts and creates initial progress, calls q2 submission, then registers active membership and emits a `create` event with `pending` status (`src/powercrud/_coordinator/manager.py:533-588`). q2's `sync=True` route can execute work before `submit()` returns according to the C3 source review. A worker can therefore publish progress or terminal evidence before the launcher performs its later writes. The terminal observation path gives a retained terminal record priority over progress, but this does not prevent late state writes or a late lifecycle event from misrepresenting the job to other consumers.

| Ordering path | Evidence and consequence |
|---|---|
| Initial progress versus worker progress | Initial progress is created before submit (`manager.py:542`). The worker starts inside submit on synchronous execution. C3 records an observed regression where the launch path's late initialization could reset progress to `pending` (`phase_C_notes.md:162`). Reproduce deterministically with a submit seam that invokes the worker and completes before returning. |
| Active membership | `add_active_task()` is called after submit returns (`manager.py:569-573`). A fast terminal path may clean active membership before this call, after which the launcher can re-add a completed task. Whether terminal handling currently removes membership on every completion route requires targeted source-level confirmation during implementation. |
| Late pending lifecycle event | The unconditional `create` event is emitted after submit with `pending` (`manager.py:574-586`). A synchronous completion can already have emitted terminal lifecycle state. The late event can initialize or overwrite consumer-facing pending state, depending on lifecycle receiver semantics. |
| Execution attachment | `state.attach_execution()` only constructs a complete `TaskIdentity` after q2 supplies an ID and does not itself write shared state (`src/powercrud/_coordinator/state.py:260-270`). Q2 pre-enqueue binding retains task identity before return (`src/coordinator_tests/test_q2_adapter.py:255-306`), but that identity has no returned execution reference yet. Audit C3 completion dispatch identity paths before selecting whether a late attachment can overwrite any persisted evidence. |
| Terminal-state ordering | `test_terminal_observation_outranks_late_progress_events` covers terminal-first observation (`src/coordinator_tests/test_lifecycle.py:615-635`). It does not establish that `_launch()` avoids the post-submit active registration and pending lifecycle event. |

**Implementation review point:** initialize whatever worker-visible identity and non-terminal state are needed before delivery; make later execution attachment and lifecycle publication conditional on the current state. Do not report a task as accepted before q2 returns a usable submission result. A deterministic in-process seam can prove sync and forced-fast ordering. Independent worker delivery remains a separate acceptance test and must not be inferred from that seam.

## Submission and cleanup

The current `_launch()` wraps submission, falsy-ID validation, and the first result checks in one `except Exception` block. That block removes conflict membership and progress for every caught exception (`manager.py:545-568`). The code does not encode whether q2 definitely rejected the work, accepted it before a later error, or started synchronous execution before raising. It also does not show launch ownership of an existing task-key reservation. A falsy ID after possible delivery has the same cleanup path as a pre-delivery rejection. q2 submission itself calls `async_task()` within a context binding and restores context in `finally` (`src/powercrud/_coordinator/q2.py:543-602`).

| Scenario | Current observable evidence and behavior | Audit assessment |
|---|---|---|
| Validation/reservation failure before q2 call | Validation precedes reservation; conflict reservation failure raises before progress creation (`manager.py:538-542`). | Definite no-submit path. Existing tests cover conflict and validation precedence (`test_lifecycle.py::test_launch_blocks_on_conflict`, `src/tests/test_async_mixin_extended.py::test_async_bulk_configuration_error_precedes_conflict_check`). |
| q2 raises before any delivery | Exception is wrapped as `Failed to enqueue async task`; conflict and progress state are removed (`manager.py:563-568`). | The repository does not distinguish this from post-acceptance errors. Need q2-source evidence for which errors prove no delivery. |
| q2 accepts work, then raises / callback or metadata path fails | The same broad exception cleanup runs if the error escapes `submit()`. Sync failure handling can dispatch captured completion evidence before re-raising (`q2.py:543-602`). | Acceptance may be uncertain and work may have executed. Blind cleanup can erase the launch's coordination evidence. Current code has no typed acceptance certainty. |
| q2 returns a falsy/missing ID | Falsy ID is raised inside the broad catch, then cleanup occurs (`manager.py:561-568`). | The code treats this as definite rejection without evidence that q2 did not deliver. Existing legacy tests assert rollback for falsey IDs (`src/tests/test_async_compatibility.py::test_all_falsey_enqueue_ids_roll_back_legacy_launch`). This test establishes current behavior, not safe rejection semantics. |
| Worker raises after beginning synchronous execution | q2 can emit worker evidence and raise before a normal returned execution reference, as recorded in C3 (`c3_audit_results.md`, sync exception discussion). | Treat separately from broker rejection. Preserve actual execution evidence and q2's propagated exception. Do not infer that no work ran. |
| Post-submit active registration fails | It is logged and suppressed, then pending lifecycle publication is attempted (`manager.py:569-586`). | Submission has returned an ID, so it may be accepted even if tracking fails. Keep failures observable and do not resubmit automatically. |

Current tests include `src/coordinator_tests/test_lifecycle.py::test_launch_rollback_on_enqueue_failure` and `::test_launch_async_task_success_without_conflicts`, and compatibility coverage for falsey IDs. They do not establish which q2 exception points guarantee non-acceptance or whether cleanup is limited to resources acquired by this launch. A C4 implementation needs an explicit internal distinction between definite rejection and uncertain acceptance, supported by q2 source or runtime evidence. Avoid adding retry behavior. Ownership-safe shared-resource algorithms remain C5; C4 can only avoid deleting state absent proof this attempt owns it.

## Caller transactions

The package's concrete launch call sites found by search are the update and delete branches in `AsyncMixin._handle_async_bulk_operation()` (`src/powercrud/mixins/async_mixin.py:405-510`). They pass model path and selected IDs to `bulk_delete_task` or model path, IDs, field data, and persistence configuration to `bulk_update_task`. The worker then resolves/querysets and performs its own database work (`src/powercrud/tasks.py:28-141,142-`). No package-level `transaction.atomic()` wraps the call to `launch_async_task()` in the view. The bulk operation mixin has atomic blocks for worker-side writes (`src/powercrud/mixins/bulk_mixin/operation_mixin.py:315-340,428-497`), after the queue launch.

| Caller | Write/transaction relationship | Commit and visibility assessment |
|---|---|---|
| Async bulk delete view | Launch submits model path and selected IDs; no preceding package-owned write or surrounding package atomic block appears in the call path (`async_mixin.py:446-480`). Worker queries and deletes selected rows (`tasks.py:28-141`). | If these rows were committed before the request, immediate submission is appropriate. If the host project wraps the request in `ATOMIC_REQUESTS` or caller code invokes this view inside an outer transaction, the worker can race the commit. This repository search cannot establish host-project settings. |
| Async bulk update view | Launch submits selected IDs and prepared field values (`async_mixin.py:450-510`). The view does not persist the requested changes before enqueue. The worker performs update work inside its own transaction (`operation_mixin.py:428-497`). | The submitted values are already materialized in task arguments, but target rows still need to be visible to the worker. Same host `ATOMIC_REQUESTS`/outer-transaction uncertainty applies. |
| Direct public launch APIs | `CoordinatorManager.launch()` and compatibility `AsyncManager.launch_async_task()` are general-purpose public entry points (`src/powercrud/_coordinator/manager.py:482-531`, `src/powercrud/async_manager.py:94-`). No package transaction policy is evident at this generic boundary. | Do not defer every public launch by default. The implementation planner should establish whether a narrowly scoped transaction-aware option is needed or whether the caller owns deferral. Current C4 notes say no new public helper is presumed. |

Checked-in `src/config/settings.py` defines `DATABASES` at line 188 but no `ATOMIC_REQUESTS` setting was found in the searched package settings. The consuming project may supply it. `transaction.on_commit()` must use the same database alias as the data transaction. The current view has no package-owned writes whose transaction can be inferred, so the audit cannot conclude that every bulk call should be deferred. The transaction requirement is conditional on a request/caller transaction or unsaved target data. A useful test seam should use `TestCase.captureOnCommitCallbacks()` or `TransactionTestCase` to establish no submission after rollback and worker-visible committed state after callback execution, with alias and nested-savepoint behavior covered where applicable.

Existing view tests cover queue invocation and bulk payload construction (`src/tests/test_bulk_view_mixin.py::test_bulk_edit_process_post_async`, `::test_async_bulk_update_submits_pickle_safe_field_metadata`, `src/tests/test_async_mixin_extended.py::test_handle_async_bulk_operation_enqueues`). They do not exercise transaction commit/rollback or a separate worker reading committed rows. Error handling currently catches launch errors in the view and routes them through its queue-failure response path (`async_mixin.py:511 onward`); deferring the enqueue would move that error beyond the synchronous request unless the response policy is deliberately defined.

## Test gaps and decisions for review

| Acceptance case | Existing evidence | Missing proof |
|---|---|---|
| Explicit sync success | q2 runtime coverage for sync signing and execution exists (`src/coordinator_tests/test_q2_adapter.py::test_q2_real_sync_signing_and_worker_keep_callable_arguments_unchanged`). | Force completion before `submit()` returns and assert progress, active membership, and lifecycle consumers remain terminal. |
| Sync exception after worker starts | C3 covers retained synchronous exception and original error propagation (`test_q2_real_sync_exception_is_retained_and_original_error_escapes`). | Launch-level assertions that broad submission cleanup does not erase execution/terminal evidence or misreport rejection. |
| Fast independent worker | Separate-process file-cache signal test exists (`test_registered_signals_cross_a_separate_process_with_shared_file_cache`). | Actual broker/worker completion racing launch registration. Preserve C3 caveat that this is not proved by current test. |
| Definite rejection | `test_launch_rollback_on_enqueue_failure` exercises mocked enqueue failure. | Demonstrate a q2 failure point that proves work was not accepted and verify only this launch's resources are released. |
| Uncertain acceptance | No located test for accept-then-raise or unknown acceptance. | Deterministically simulate accepted work followed by submission/metadata error; verify no blind retry and no unsafe cleanup. |
| Ownership-limited cleanup | Conflict cleanup and falsey-ID rollback tests assert removal. | Replacement/pre-existing owner safety is C5 territory. C4 must test not releasing resources it cannot prove this launch owns. |
| Rollback prevents submit | No launch transaction test found. | Register callback within outer transaction and roll back; assert broker seam is never called. Include nested savepoint rollback and correct DB alias if package adds `on_commit`. |
| Saved data visible to worker | Worker CRUD tests cover business operations but not commit visibility. | Commit data, execute deferred callback against a separate transaction/connection or worker, and verify rows/values are visible. |

Decisions for the C4 implementation planner:

- Define how submission outcomes are represented internally. Determine from q2 1.11.1 source which exceptions are definitely pre-acceptance; classify all other failures as uncertain unless evidence proves rejection. Verify the deployed supported q2 version before relying on version-specific behavior.
- Select launch-state ordering that preserves terminal evidence and prevents a late pending event or active registration from restoring non-terminal state. Keep a usable execution identity for worker callbacks that can arrive before `submit()` returns.
- Decide transaction deferral only for launch sites that depend on an uncommitted transaction. Check host integration's `ATOMIC_REQUESTS`/outer transaction configuration. If deferring a bulk view launch, define its HTTP success/error semantics because an `on_commit` callback runs after the synchronous response path has committed.
- Keep actual ownership/conditional release mechanisms with C5. C4 should not add a cleanup path that guesses ownership. Keep reconciliation and administrative cleanup with C6.
- Add reusable lifecycle/submission tests under `src/coordinator_tests/` and caller/transaction tests under `src/tests/`. Run them through `./runproj exec` when implementation is authorized. Do not close issues 1–13 from C4 completion alone.
