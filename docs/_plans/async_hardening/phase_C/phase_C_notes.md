#### C2.1 feasibility findings — 2026-11-11

**Result: feasible at the design level for C2, using records that are created once and q2's existing signals.** This was repository and dependency-source inspection, not a worker experiment or backend concurrency test. C2 must not implement a shared read/modify/write task document or depend on conditional updates being available through Django's common cache API. The later lifecycle and ownership guarantees still need their assigned C3–C6 implementation and evidence.

**Discussion decisions:** The user accepted raising the q2 minimum when the missing worker-exit signal in older versions was explained. Use `django-q2>=1.11.1,<2`; `uv.lock` already selects 1.11.1, so this changes the declared compatibility floor, not the locked q2 version. That supersedes the earlier tentative choice to limit automatic context to built-in/decorated workers. A proposed narrowing of the broad shared-cache claim was **not approved**. The user asked for further investigation; the design below avoids requiring that policy change for C2. Preserve Redis, Memcached, DatabaseCache, and the existing support position. File-cache suite results remain limited baseline evidence.

| Finding | Evidence | Design consequence |
|---|---|---|
| q2 knows its execution ID before delivery. | [q2 1.11.1 submission](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/tasks.py): `pre_enqueue` receives the prepared task before signing, synchronous execution, or broker enqueue. | Capture the actual execution ID and effective result route there. Nothing after `submit()` returns needs to rewrite identity. Capturing an ID does not prove broker acceptance. |
| Context can be scoped without replacing the callable. | [q2 1.11.1 worker](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/worker.py) sends `pre_execute` before invoking the original function and `post_execute_in_worker` afterward, including its explicit synchronous-exception branch. [q2 1.9.0 signals](https://github.com/django-q2/django-q2/blob/v1.9.0/django_q/signals.py) lacks the latter signal. | Use paired signals at the approved 1.11.1 floor. Keep context tokens in process-local state, never in the serialized task. Restore the caller's context in adapter `finally` handling as well, covering synchronous signal failures. |
| Hooks need metadata outside the original callable's arguments. | [q2 monitor](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/monitor.py) constructs saved Tasks from the task dictionary's kwargs. Cached results preserve the task package. | Carry a versioned envelope as a top-level task field. After the worker has returned, copy that envelope into result kwargs for existing hook reconstruction. The function receives no additional legacy kwargs. |
| Application configuration is not restricted to JSON. | [q2 signing](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/signing.py) uses pickle; tracking exports `AsyncDashboardConfig`, including supported importable formatters. | Retain supported Python configuration values inside versioned mappings; validate serialization/importability rather than stringifying configuration or keeping only dictionaries. |
| The common cache interface does not supply compare-and-swap. | [Django cache interface](https://github.com/django/django/blob/stable/5.2.x/django/core/cache/backends/base.py). [DatabaseCache](https://github.com/django/django/blob/stable/5.2.x/django/core/cache/backends/db.py) can update an expired row during `add`; [file-cache add](https://github.com/django/django/blob/stable/5.2.x/django/core/cache/backends/filebased.py) is check-then-set. | Avoid updating shared identity records, finite-lived claims, and expiry/replacement cycles in C2. Do not describe generic `get`/`set` or a temporary cache lock as conditional-update proof. |

**State design:** Add the internal `TaskIdentity` representation and `_coordinator/state.py`. Persist a version-1 mapping containing the logical key, `ManagerSpec` mapping, coordination snapshot, and complete `ExecutionRef` mapping at `{key_namespace}:async:task:{task_key}`. The manager spec/config is prepared in memory before reservations. At `pre_enqueue`, `attach_execution(prepared_identity, execution)` creates the complete mapping and calls create-only `put_identity`; it does not update a previously published record. `get_identity(task_key)` reads and validates that record only in the caller's selected location. These are internal interfaces, not a new backend or public settings source.

Use non-expiring `cache.add(..., timeout=None)` for published identity. The key belongs to one logical job while retained. A repeated identical internal write is idempotent; a different execution or manager/configuration at the same key is an error, never an overwrite. Verify the saved record before permitting delivery; distinguish an existing conflicting record from a failed/unavailable write. There is no worker-side recreation, post-submission attachment, or read-time refresh. Missing/corrupt/expired identity is unknown. A cache eviction or restart can still lose evidence; this design does not promise recovery from that loss.

**Retention:** Keep identity non-expiring while work is live. On confirmed terminal execution evidence, create a separate versioned marker at `{key_namespace}:async:task:{task_key}:finished:{execution_id}` with the finish time and absolute identity expiry, using the retained `terminal_result_ttl` (24 hours by default). For C2, worker evidence qualifies when a finish time exists and q2 reports success, or reports failure with effective `ack_failure=True`. A failed attempt that q2 may redeliver is insufficient; retain identity without starting its expiry clock until finality can be established. This marker is also create-only and non-expiring physically: duplicate/late events cannot refresh it. `get_identity` checks the marker for the execution in the identity and treats its absolute deadline as logical expiry. It never treats marker absence as proof that work is running or successful. The marker holds retention evidence only, not C3's business outcome/result snapshot. The synchronous-exception signal may lack finish/result fields; reset context but do not invent terminal evidence in that case.

This arrangement separates identity, execution evidence, and later outcome records. It avoids a completion overwriting identity and prevents an old execution's marker changing a newer execution's retention. Physical reclamation of the immutable records is assigned to C6 after C5 supplies ownership-safe removal; C2 must record the interim accumulation of bookkeeping and must not use read/check/delete to reclaim or replace it. Explicit logical keys cannot be reused while their records remain physically retained; generated UUID keys naturally satisfy that requirement. No safe-reuse guarantee after arbitrary cache loss is introduced.

**Limits of the checkpoint:** Redis and Memcached provide native atomic creation for non-expiring records; DatabaseCache's unique cache key prevents competing inserts of a fresh, non-expiring key. This avoids relying on its expired-row replacement path. These are source-level feasibility observations, not certified concurrency guarantees. Existing configured serializers, storage limits, write-error suppression, key transformations, and physical eviction still require regression coverage. Backend-specific conditional update/removal operations remain candidates for C3–C6, not C2 requirements or a new support policy. General registry races, resource leases, fencing of disconnected workers, broker redelivery, and crash recovery remain open.
