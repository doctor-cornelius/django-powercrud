## Current ownership paths

`_launch()` reserves the requested object locks through `add_conflict_ids()`, then calls `add_active_task()` without lock IDs before q2 delivery can begin. `complete()` retains terminal evidence before `remove_active_task()`, which removes registry membership, conflict locks, and progress. `register_descendant_conflicts()` reuses the manager in task context when available and calls `add_conflict_ids()` for IDs discovered during work ([manager.py](../../../../src/powercrud/_coordinator/manager.py#L535), [context.py](../../../../src/powercrud/_coordinator/context.py#L106)).

The active registry is a cached set. `add_active_task()` and `remove_active_task()` each read the whole set, change it locally, then overwrite the key. Two launchers can both read `{}` and write `{A}` and `{B}`, losing one membership. A launch racing completion can likewise restore or drop an unrelated task. The per-task lock index has the same read/modify/write shape: `add_conflict_ids()` reads its set, unions newly acquired lock keys, and writes it back. Concurrent descendant registrations can overwrite one another's additions. `remove_conflict_ids()` reads this index, deletes its referenced lock keys, and deletes the index key without an atomic ownership check.

Per-object acquisition uses `cache.add(key, task_name, conflict_ttl)`, so an existing lock held by the same `task_name` is still treated as a conflict. Partial-acquisition rollback and normal cleanup use unconditional `cache.delete()`. For example, task A acquires X, pauses, X expires, task B acquires X, then A's rollback or completion deletes X. Looking up the value before deleting cannot prevent the replacement between the read and delete. If cache failure occurs during acquisition, rollback has the same ownership problem and the function can leave partial state. A failed index write after successful object acquisition can also leave acquired locks without a complete cleanup index.

Repeated descendant registration is expected in this path. `Book.save()` persists the changed book, reads its resulting genre IDs, then registers them. Two books assigned the same genre in one bulk job cause the second registration to encounter the job's existing genre lock and fail under current `cache.add()` semantics. The worker's bulk persistence wraps writes in a transaction, catches the exception, and reports a failed result after rollback ([Book.save()](/home/mfo/projects/packages/django_powercrud/src/sample/models.py#L156), [bulk update persistence](/home/mfo/projects/packages/django_powercrud/src/powercrud/mixins/bulk_mixin/operation_mixin.py#L423), [bulk worker](/home/mfo/projects/packages/django_powercrud/src/powercrud/tasks.py#L142)). This is the likely shared-genre explanation. The incident trace did not include the genre ID or current lock owner, so a competing task is not excluded.

The existing coverage in [test_state_locks.py](/home/mfo/projects/packages/django_powercrud/src/coordinator_tests/test_state_locks.py) covers sequential reservation, conflict rollback, set layout, and idempotent cleanup. Despite its name, `test_concurrent_atomic_reservation` runs two reservations sequentially. `test_context.py` verifies manager invocation and that a rejected descendant registration stops following work, but it does not exercise repeated same-owner registration or real shared-cache concurrency. Coordinator settings use file-based cache. These are useful baselines and do not establish cross-process behavior for the claimed backends.

## Backend capability inventory

The repository claims Redis, Memcached, and DatabaseCache in async documentation and names all three in the runtime error for unsupported local cache ([async reference](../../../../docs/mkdocs/reference/async.md#key-settings), [manager.py](/home/mfo/projects/packages/django_powercrud/src/powercrud/_coordinator/manager.py#L419)). The configured Django cache interface currently supplies `add`, `get`, `set`, and `delete`; that API does not expose a portable compare-and-delete or compare-and-renew operation. The findings below describe possible backend mechanisms and gaps for investigation, not a selected design.

| Backend | Claim and available mechanisms | C5 question and evidence needed |
|---|---|---|
| Redis via django-redis | The repository depends on django-redis and its documentation describes raw Redis client access. Redis supports atomic scripts and conditional key operations, which could implement ownership compare-and-delete, compare-and-renew, and atomic set/index changes when executed against the authoritative primary. These operations are outside the generic Django cache API. | Identify supported client/topology and how custom operations reach the same primary used by `cache.add()`. Check key serialization/prefixing, Redis failover semantics, script/command permissions, and retry behavior. Verify synchronized separate-process acquisition, renewal, and release against the claimed deployment configuration. Source capability is not proof for every django-redis client or topology. |
| Memcached | The repo's validator explicitly lists Memcached, but no dedicated Memcached configuration or test was found in the audited suite or support notes. Django's cache API offers atomic `add`, but ordinary `get` then `delete` is not conditional. Client-specific CAS may permit compare-and-swap if the deployed Django backend exposes it safely. Memcached has no multi-key transaction for updating the active set and per-task index. | Pin the Django backend and client library/version actually intended. Establish whether CAS is available through the supported interface and how CAS tokens survive serialization and expiry. Determine whether a registry/index can be updated without lost changes using only supported primitives. No synchronized Memcached evidence is present. |
| DatabaseCache | Documented as a supported shared backend and exposed through Django's cache API. `add` is intended as insert-if-absent; cache mutation is persisted in the configured database. Generic API still has no compare-and-delete. Concurrent set updates may use database locking/conditional updates only through backend-specific or direct database logic. | Establish supported database engines, transaction isolation, cache-table maintenance, and whether cache operations share a database/transaction with application writes. Inspect the exact Django version's DatabaseCache implementation and reproduce competing writers, expiry, and conditional ownership updates with separate processes. No synchronized DatabaseCache evidence is present. |

Other shared caches may be accepted by the current validator because it rejects LocMem/Dummy by class-name matching rather than testing an operation contract. This audit did not establish the full downstream support boundary. Do not infer support for arbitrary Django cache backends from that validator.

## q2 job lifetime and stale delivery

The project pins the q2 dependency range to `>=1.11.1,<2`; the C4 record's controlled broker test did not establish cluster dispatch or backend races ([pyproject.toml](/home/mfo/projects/packages/django_powercrud/pyproject.toml#L30), [C4 verification](phase_C_notes.md#c4-implementation-and-verification)). The adapter prepares retained identity and conflict reservations before its `before_delivery` path submits work ([q2.py](/home/mfo/projects/packages/django_powercrud/src/powercrud/_coordinator/q2.py#L543)). At worker start, `_pre_execute()` verifies retained identity, reconstructs the manager/context, and writes a worker-start marker. If that validation raises, q2 should not call the task body on that execution path. This audit did not execute q2 or verify whether broker retry/redelivery can later invoke it again.

The repository exposes q2 timeout, retry, `ack_failure`, broker selection, and result-storage options through its adapter. q2 documentation states that a broker supporting receipts can make a task available again after `retry` seconds, and that when retry is shorter than execution time the same task may be started more than once. This means queue wait consumes the lock TTL before worker start, while long-running work can outlive both the lock TTL and receipt interval. The documented PowerCRUD defaults are `CONFLICT_TTL=3600` and project `Q_CLUSTER.retry=300`; q2 documents a generic default retry of 60 seconds. Effective per-deployment values must be inspected before proposing timing guarantees ([async reference](../../../../docs/mkdocs/reference/async.md#key-settings), [project settings](/home/mfo/projects/packages/django_powercrud/src/config/settings.py#L202), [q2 configure documentation](https://github.com/django-q2/django-q2/blob/v1.11.1/docs/configure.rst#retry)).

The coordination cache, q2 broker receipt, and q2 result storage are separate mechanisms. Broker redelivery can create duplicate workers while the first worker continues. A refreshed busy marker can signal current ownership to other coordinator operations, but arbitrary callable code can continue writing unless each write is fenced or checks ownership. Built-in PowerCRUD bulk writes can potentially check a task ownership/version condition around persistence, but a transaction-wide check alone may race with ownership loss unless the database write itself enforces the fence. Generic user callables do not receive automatic fencing at every side effect. Cancellation cannot be inferred from a failed renewal. The audit therefore cannot claim that renewal alone prevents stale writes or that a crash can safely release work while the original process may still be alive.

The lifetime design remains open across queue wait, receipt expiry, long jobs, stale delivery, renewal failure, and crash recovery. Any strategy must state what it guarantees for coordinator lock visibility and what it can guarantee for application writes. It must also state the response to renewal failure and how recovery proves the old worker can no longer write. No strategy or timing limit is selected here.

## Verification matrix for implementation

| Scenario | Redis | Memcached | DatabaseCache | Required observation |
|---|---|---|---|---|
| Concurrent active-registry add/remove with unrelated entries | synchronized processes | synchronized processes | synchronized processes | No unrelated membership is lost. |
| Competing reservation for one object | synchronized processes | synchronized processes | synchronized processes | Exactly one owner is accepted while live. |
| Partial acquisition failure and rollback | synchronized processes | synchronized processes | synchronized processes | Rollback releases only locks still owned by the failing task. |
| Expiry and replacement-owner reacquisition during rollback/release | synchronized processes | synchronized processes | synchronized processes | Old task never removes replacement protection. |
| Repeated/overlapping descendant registration | queued consumer regression plus shared backend | queued consumer regression plus shared backend | queued consumer regression plus shared backend | Same owner can add an existing resource; other owner blocks; the complete index remains. |
| Stale queued delivery and q2 receipt redelivery | real broker/worker plus cache | real broker/worker plus cache | real broker/worker plus cache | Duplicate/stale worker cannot erase protection or write after the accepted ownership policy says it must stop. |
| Long job through lease renewals | multi-process worker | multi-process worker | multi-process worker | Protection stays effective for the declared supported duration. |
| Renewal failure while work continues | inject backend/connection failure | inject backend/connection failure | inject backend/connection failure | Defined failure behavior and observed write protection or explicit limitation. |
| Worker crash and recovery | kill separate worker | kill separate worker | kill separate worker | Recovery is safe and does not unlock work that can still write. |

PowerCRUD consumer regression cases: queue an update assigning the same genre to two books and assert both changes commit; then hold that genre lock under a different task, queue the same two-book update, and assert both book writes roll back and the other task still owns the genre lock. Reusable lock/context behavior belongs in `src/coordinator_tests/`; queued bulk consumer behavior belongs in `src/tests/`.

## Questions for C5 discussion

1. Which supported backend-specific operations can provide atomic same-owner idempotent acquisition, ownership-conditional release/renewal, and non-losing registry/index updates on the actual claimed deployments?
2. What is the supported relationship between queue wait, q2 receipt retry, task timeout, conflict TTL, and any renewal interval?
3. What must happen when renewal fails, and what evidence permits recovery to release a lock while a worker might still be running?
4. Which stale-worker protection is enforceable for built-in bulk writes, and what guarantee can be made for arbitrary callables that write outside coordinator-controlled code?
5. What synchronized multi-process and real q2 worker environments will be used to produce acceptance evidence for Redis, Memcached, and DatabaseCache?

No C5 implementation algorithm or backend support change is proposed by this audit. C6 retains ownership of reconciliation and force cleanup.
