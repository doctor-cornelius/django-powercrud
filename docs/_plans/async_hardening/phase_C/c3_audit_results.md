# C3 audit results — 2026-11-11

## Verdict

The three C3 checklist items cover the required outcomes: distinguish execution from business results, retain monotonic terminal state, and deliver completion across claimed q2 modes. No checklist change is indicated. The implementation decisions recorded as open in [Phase C notes](phase_C_notes.md#open-technical-decisions) are still necessary; the checklist alone does not resolve them.

The initial audit inspected `async_hardening/phase_c`, HEAD `da1384931886ddad9597570bb50740c9617c51de`, starting from a clean working tree. The inspected commits were `683cc72d` and `da138493`. Recommendations were reviewed and refined on 2026-11-11 against the current code, agreed A1/B1 contracts and tagged q2 source. Only this report was written. No tests were run. C2 evidence below is taken from its recorded verification, not rerun here.

## Findings

- **Execution and business result are conflated.** `Completion` contains q2's `success` and raw `result`, with no explicit business outcome ([types.py:128](../../../../src/powercrud/_coordinator/types.py#L128)). `AsyncManager.complete()` maps q2 success directly to success, removes active state before reporting, and treats unknown as a `complete` event ([manager.py:1150](../../../../src/powercrud/_coordinator/manager.py#L1150)). The tracking mixin maps `complete` to success and lets later create/progress events rewrite stored status ([tracking.py:181](../../../../src/powercrud/_coordinator/tracking.py#L181)).
- **Polling can still invent success.** C2 changed missing identity/progress handling to unknown, and the C2 test was updated accordingly. But cache-only status maps the outcome-free finish marker to `completed` ([manager.py:668](../../../../src/powercrud/_coordinator/manager.py#L668)); the endpoint then returns success ([views.py:10](../../../../src/powercrud/_coordinator/views.py#L10)). The marker stores only finish/expiry timestamps ([state.py:102](../../../../src/powercrud/_coordinator/state.py#L102)). Thus the issue register's “missing progress is completed” observation lags C2, while issue 6's broader missing/expired/unavailable and failure-preservation requirement remains open.
- **Bulk workers discard useful results.** Built-in workers turn a result dictionary into `bool(result.get("success"))`, then return only that bool ([tasks.py:27](../../../../src/powercrud/tasks.py#L27)). The operation layer has `success_records` and `errors`, but update failures return zero successes whenever errors exist ([operation_mixin.py:500](../../../../src/powercrud/mixins/bulk_mixin/operation_mixin.py#L500)); delete catches a batch exception outside `transaction.atomic()` and returns its incremented count after rollback ([operation_mixin.py:307](../../../../src/powercrud/mixins/bulk_mixin/operation_mixin.py#L307)). Counts must not be labeled committed effects without verifying transaction/backend semantics. Existing unit tests mock bulk failures and do not test outcome translation through q2.
- **Unknown polls forever in the sample.** The endpoint returns `poll_interval: 1000` for unknown. Both sample detail templates treat unrecognized status as in-progress; neither stops polling on unknown. The API and UI need a reason and a finite-stop rule.
- **Optional reporting is partly isolated already.** `_emit_lifecycle()` catches callback exceptions, but `complete()` wraps cleanup and callback reporting together; a cleanup exception can prevent outcome reporting. State publication should be authoritative and precede best-effort cleanup/tracking. Reporting failure must not erase execution evidence.

## q2 completion delivery

The declared minimum is `django-q2>=1.11.1,<2`; recorded C2 tests use q2 1.11.1. Version-matched source inspected: [task submission](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/tasks.py), [monitor/result storage](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/monitor.py), [worker signals](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/worker.py), and [hook dispatch](https://github.com/django-q2/django-q2/blob/v1.11.1/django_q/signals.py). Context7 docs corroborate that worker and monitor signals run in different processes. No live broker/result-mode experiment was run in this audit.

Transport and result storage are separate dimensions: repo settings use q2 ORM broker with a Redis coordination/result cache, while project docs claim Redis, Memcached and DatabaseCache as coordination backends and expose q2 options. The adapter also validates ORM, Redis, SQS, Mongo, IronMQ and custom broker selections. This is an inventory of code/docs claims, not proof each deployment mode is runtime-supported.

| Result path | q2 1.11.1 behavior | Current PowerCRUD completion consequence |
|---|---|---|
| Saved ORM `Task` | `monitor.save_task()` saves/updates a model; `post_save` invokes the task hook. Positive `save_limit` prunes older successes. | Existing hook can run, but outcome is interpreted as execution success only. Pruning can remove historical rows; it is not itself a completion signal. |
| `cached=True` / cache TTL | `monitor.save_cached()` writes to broker cache and does not save a `Task`; monitor then emits `post_execute`. | Model `post_save` hook is bypassed. C2 proves real synchronous cached lookup, not automatic lifecycle completion. |
| Successful `save=False` / negative save limit | `save_task()` returns without a `Task`; monitor still emits `post_execute`. | Hook is bypassed; completion may be absent. Failures are still saved by q2's source branch. |
| Custom q2 hook | Replaces the configured hook on saved ORM `Task` records. Cached/skipped-save paths do not invoke it. | Internal completion hook is bypassed when a custom hook replaces it. The monitor signal remains independent. |
| q2 `q_options` | q2 1.11.1 lets `q_options` override individual options; explicit `task_name` is chosen before `q_options.task_name`. Adapter records effective options but has a special explicit-name rule. | Audit each effective save/cache/hook/ack setting; do not infer behavior from defaults alone. |
| Failure / redelivery | Worker emits `post_execute_in_worker` before monitor persistence. Normal monitor acknowledgement accepts success or `ack_failure`; ORM `save_task()` can additionally acknowledge when `max_attempts` is reached. Failed ORM results can invoke the hook on each saved attempt. | Current worker retention marker avoids expiry for failures without acknowledgement policy, but ORM hook can still publish failure/cleanup on a potentially redeliverable attempt. Finality cannot be inferred from a saved failure or `ack_failure=False` alone. |
| `sync=True` | q2 1.11.1 runs worker and monitor inline. A synchronous worker exception emits the worker signal then raises before the ordinary result handoff. | C2 recorded ordering regression: later launch registration can reset progress to pending; C4 owns that fix. C3 must not claim the synchronous exception has a normal terminal result when q2 supplies none. |

**Refined delivery recommendation:** publish qualifying terminal evidence from `post_execute_in_worker`, before q2 result storage or optional hooks. Feed worker evidence, ordinary hooks and any monitor fallback into the same identity-checked terminal publication operation. A monitor `post_execute` receiver is a candidate for completion handling where ORM hooks are absent, and for repairing a failed worker-side publication while the result dict is still available. It is not guaranteed delivery: storage/control-flow errors or acknowledgement exceptions can prevent it from running. Receiver registration must be verified in the monitor process, and receiver errors must not escape into q2's monitor loop.

Do not dispatch an application's hook/manager override through both routes merely because core publication is idempotent. B1 requires the actual q2 `Task` for saved legacy callbacks and preserves overrides that do not call `super()`. A task dict is not that object. Keep q2 custom-hook selection and invocation intact; define coordinator fallback and legacy override behavior explicitly for cached/unsaved results before adopting a second reporting route. Internal snapshot publication must remain independent of an application's decision to perform custom reporting or cleanup. Exactly-once arbitrary callback delivery is not a supported promise.

**Synchronous exceptions require a dedicated path.** The worker signal runs before q2 fills `success`, `result` and `stopped` in its sync exception branch. C3 must capture actual exception evidence at the signal/submission boundary and retain a truthful execution failure, preserving q2's propagated exception. A signing, enqueue or receiver failure must not be relabeled a business-call exception. This design gap must be resolved in the implementation plan; simply leaving all sync exceptions unknown would not meet A1. C4 still owns late registration and rollback/submission ordering.

A1/Q6 settles failure acknowledgement on by default for PowerCRUD's non-idempotent work, but current adapter fallback reads `ack_failures=False` and no explicit default is visible at the PowerCRUD launch boundary ([q2.py:474](../../../../src/powercrud/_coordinator/q2.py#L474)). Supply that default in the PowerCRUD boundary, preserving explicit application/q2 choices and the reusable coordinator's independence. `ack_failure=True` is a policy, not proof of successful broker acknowledgement or absence of duplicates. For explicit retry configurations, saved failure alone must not terminalize/release work. q2's ORM attempt-limit acknowledgement is separate evidence to investigate; cached results do not provide the same saved attempt count. Keep insufficient finality evidence unknown without adding an attempt-history/retry system.

## State and consumer recommendation

- **Explicit business result:** recommend a dedicated importable outcome type, with success/failure/partial, counts and useful errors. A plain dict remains an ordinary return even if it has identical field names. Keep execution success separate; partial business success maps to overall `failed` with partial details, preserving the agreed five public states. Translate PowerCRUD's known result dictionaries at the consumer boundary. Keep transaction semantics unchanged; correct misleading rollback counts and use unknown counts where a custom backend cannot substantiate committed effects.
- **One terminal record:** evolve the existing per-execution finish record to hold both bounded outcome and absolute expiry in one versioned, create-only publication. Avoid separately writing an outcome and retention marker with no atomic operation joining them. Existing retention-only evidence may establish expiry but cannot establish success. Verify the stored value after publication, reject mismatched identities, and report conflicting terminal evidence without replacing the accepted record or extending expiry. Redelivery may reuse the same q2 ID; an ID match is not an attempt identifier. Prevent expiry/late-event recreation from starting a fresh retention period.
- **One observation:** status, polling, tracking and cleanup-facing outcome classification should share the retained interpretation. Terminal evidence takes precedence over progress. Unknown observation is not proof that execution ended. Optional tracking needs guarded database updates: checking the cache and then saving a model is insufficient against a progress write already in flight. Keep reusable mapping and state rules independent of PowerCRUD settings/models.
- **Payload bound:** recommend a configurable 16 KiB serialized snapshot limit as an implementation default, with depth/item/string bounds, counts preserved, and explicit truncation/unrepresentable markers. This is a proposed engineering default, not an agreed requirement. Bound retained display data only; preserve the callable's raw q2 return semantics. Formatter/serialization errors must not change execution success.
- **Finite unknown polling:** recommend stopping the current automatic polling session on unknown, displaying its reason and permitting manual refresh. This avoids introducing a retry timer or mislabeling unknown as job completion. Keep any polling-stop flag separate from job-terminal state; preserve existing terminal HTTP behavior where compatible. A more elaborate automatic retry policy is optional product work, not a prerequisite for C3.
- **Safe publication and reporting:** an immutable terminal record plus terminal-first reads is the smallest candidate; a generic cache check/set or expiring lock does not prove it safe. Check create-only/expiry behavior on Redis, Memcached and DatabaseCache, then obtain synchronized evidence before claiming concurrency guarantees. Keep C5's registry/lease algorithms and C6's physical reclamation boundary. Core state/cleanup failures remain observable; optional tracking failure is best effort and repairable from retained evidence without guaranteed callback replay.

## Verification gaps and ownership

Reusable coverage belongs in `src/coordinator_tests/`: explicit outcomes versus plain `False`/`None`/dicts; partial bulk result serialization; unknown reasons; terminal expiry; duplicate/stale callback; late create/progress; state-write and reporting failures; synchronous exception; failure acknowledgement/redelivery; and q2 real monitor delivery across ORM, cached TTL, `save=False`, pruning, custom hook, and effective `q_options`. Include custom broker routes only where the support inventory claims them. Existing C2 real q2 tests cover sync signing/execution and cached lookup, but do not exercise automatic completion delivery across these modes.

PowerCRUD owns `src/tests/` and sample consumer tests: bulk translation with truthful post-transaction counts/errors, legacy hook/override behavior, progress endpoint compatibility, and both DaisyUI/Bootstrap unknown/failure/partial displays. Existing sample tracking tests call lifecycle methods directly; they do not exercise q2 completion delivery. No issue 1–13 is closed by this audit.

Keep boundaries explicit: C3 owns outcome meaning, terminal snapshot, polling/tracking and completion delivery. C4 retains submission/late-registration ordering and transaction-safe launch. C5 retains backend concurrency, registry ownership and leases. C6 retains reconciliation, physical reclamation and force cleanup.

## Next step

Prepare a concrete C3 implementation plan from the refined recommendations. No broad second audit is needed. The plan must resolve three remaining technical details from source inspection and, where needed, tightly scoped feasibility verification: sync-exception evidence capture; saved-hook versus monitor-fallback dispatch preserving legacy overrides; and atomic terminal publication/expiry with guarded tracking writes. Treat worker and monitor signals as complementary evidence, not guaranteed notifications.

Present the outcome type, proposed 16 KiB display bound and stop-on-unknown polling behavior as recommended defaults for discussion. Keep the agreed 24-hour retention and ordinary-return semantics settled. The plan should name the owning changes and acceptance tests, including the missing q2 result-mode coverage, then stop for design agreement before implementing C3.

Source-version limitation: upstream runtime/source claims above are pinned to django-q2 1.11.1. The declared range is `>=1.11.1,<2`; no evidence here establishes identical signal/monitor behavior across every later 1.x release or every broker service.

## Implementation follow-up — 2026-11-11

C3 was subsequently implemented on `async_hardening/phase_c`. The selected choices are `BusinessOutcome`, a 16 KiB bounded terminal display payload, immutable create-only terminal snapshots with completion-based logical expiry, q2 worker publication plus monitor fallback under a shared dispatch claim, and a stateless 30-second unknown viewing budget. Details and verification are in [Phase C notes](phase_C_notes.md#c3-implementation-and-verification--2026-11-11).

Focused q2 runtime tests cover synchronous saved, cached, `save=False`, custom-hook, and synchronous-exception paths. They do not prove delivery through a separately running broker/worker or every pruning, attempt-limit, and declared q2-version combination. The separate-process file-cache test covers signal/envelope identity handling, not broker delivery. Terminal publication and guarded tracking were tested sequentially; synchronized races across Redis, Memcached, and DatabaseCache remain unverified. These are evidence limits, not grounds to reduce the claimed support matrix. C4 late registration, C5 resource ownership/concurrency, and C6 reconciliation/reclamation remain outside C3.
